# 精准行走：保留等待原游戏放行的新方向

2026-10-11，Linux 实盘验证。该修复沿用 `PAL_RESPONSIVE_INPUT=1`，不增加模式，不改变默认开关。`v0.1.0-preview.1` 已发布附件未替换，其中尚不含此修复。

## 复现与原因

正常流程完成玉佛寺后，在黑水镇入口（scene 62）发现：玩家已经松开旧方向，再按 DOWN，90 个 VBlank 内不移动；菜单仍可打开，正常保存/退出菜单后恢复。碰撞地图与原盘一致，实时事件位置也未挡住该格。独立新进程重放复现了两个检查时刻的完整 RGB 画面。

只读探针保留了原执行结果，并定位到 VB 7959–7961：原游戏的 `06076A09=FF` 释放门尚未清除。精准输入将这一短暂状态当作失去控制，清掉了新方向并要求再次释放；VB 7962 原门已经解除，方向却继续被抑制。

这个原游戏标志不只用于菜单。音效资源装载函数 `0603237C` 也会设置它；原输入扫描在检测到 guest 按键缓冲为空后清除它。黑水镇有环境音效自动脚本。因此不能将 FF 本身等同于进入剧情。

## 改动边界

- 处于既有野外采集窗口时，可以保留新方向，FF 仅暂停实际消费。
- FF 未解除之前不移动、不取出待处理方向，也不改写原游戏的 FF 标志。
- 非移动 action、DC、菜单、脚本及切场仍按原逻辑清空；旧方向跨真实控制边界后仍须释放再按。
- 可选 wake 条件仍检查原游戏已放行，避免采集与提前唤醒混用。
- 原版模式完全不执行这些 hook。CPU、音频、CD、战斗与显示队列代码未改。

这修复的是已经松开后的新按键被丢弃。原游戏环境音效装载所设置的释放门，以及长按跨该原有门的行为，本轮没有取消。更广的首步/显示优化仍是单独候选。

## 验证

- 原 wrapper 的针对性测试失败；新 wrapper 通过 720 组方向、短按长度、相位和门延迟组合。
- 五种真实边界模型（显式 clear、非移动 action、DC、scene、跨 VB 脚本）没有方向泄漏；FF 内完整短 tap 在解除后恰好消费一次；wake 不越过 FF；原版关闭路径无操作。
- 真盘相同输入：VB 7959 的修复前后世界坐标和 RGB 完全一致。原版精准 wrapper 之后仍停在 `(1392,1320)`；候选在 VB 7961 消费 DOWN，继续行走并自然进入南侧转场。正常退出，源存档及测试存档 hash 不变。
- 既有原版首战 12/12、精准行走 94/94、快速群体法术 44/44 检查图与参考 RGB 完全一致，对应 BUP 也一致。
- 无输入冷启动至 7000 VB 的 10/10 检查图与参考 RGB 一致，正常退出。
- `tools/tests`：配置已有上游 runtime 后 149 passed、35 subtests passed，无跳过（未提供可选 runtime 的首轮为 148 passed、1 skipped）。
- `PYTHONPATH=validation python -m pytest validation/tests -q`：26 passed、8 subtests passed。
- 从原生成器重新生成，再运行正式 options 安装器，140 个生成源码/运行时文件与实际测试候选逐字节一致（版本 manifest 单独核验）。源文件 hash 和 options 版本已更新，旧构建不会被静默当作新版本。

候选 Linux 可执行文件 SHA256：
`fdd3c2f6a23d5421171f753e1a4b2440d2cd123d70d8d7c00bb1fdd39c6ff7b4`

本轮尚未在 Windows 原生运行该补丁；此前 Windows 发行包的可玩反馈不能替代本轮 Windows 验证。这里也不将headless VBlank 执行耗时当作用户端输入延迟。

## 从源码更新

先保留自己的存档及本地修改。更新当前测试分支后，使用现有 Windows 构建说明中的 SDL 路径重新生成，例如：

```powershell
python tools/winbuild.py build --pal-options --recompile --sdl-dir "你的SDL3Config.cmake所在目录"
```

`--recompile` 是必要的；不要只复制源码后继续运行旧 exe。继续使用原有 `PAL_RESPONSIVE_INPUT=1`；其余选择按现有说明。此提交不替换已发布 Release 附件。
