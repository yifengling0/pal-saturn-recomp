# SH-2 16-byte DMA burst short-copy fix

## Reproduction and cause

On the pinned upstream `086c372c67d9e0f94fcc64cedd6e6b63cc5542b5`, `runtime/src/machine/onchip.cpp::dma` computes `n=tcr/4` for 16-byte bursts. Its loop then also advances `i` by an extra three after every burst. A 64-byte request (TCR=16 longwords) copies only 16 bytes, then clears TCR and sets transfer-end. The byte/word/longword paths are not changed.

`patches/0005-sh2-dma-burst-count.patch` removes only that extra `i += 3`. The loop already counts bursts, so each iteration must perform exactly one burst.

## Real-image evidence

The game loads map data from MGOP.JOE through PROG `f_0602F118`, then invokes its DMA wrapper `f_0605D4DC`:

- `0602F29E`: source `00200000`, destination `0608C310`, length `0x10000` map bytes
- `0602F2B2`: source `00210000`, destination `25C10000`, length from `060769C4` for tile textures
- `f_0605DA60`: waits for the DMA status to indicate completion

For the map at MGOP.JOE sector offset `0x4CF`, the file and post-read source contain 3,953 nonzero bytes, FNV-1a `3AC122B5`. After the original DMA, the destination has 1,379 nonzero bytes, FNV-1a `520FBFDF`. Reconstructing only the first `0x4000` bytes with the previous map's remaining bytes reproduces this exactly. The texture request is `0x25DA0` bytes, but only `0x9770` bytes match the source in the VDP1 dump, exactly one quarter.

The 330 black tile commands are generated by `f_060344A0` (15 rows × 11 columns × two halves). Map lookups at `060345D8` and `0603483E` read `0608C310 + 8*x + 512*y` and the adjacent half. The map's uncopied rows contain zero indices; tile zero is genuinely a black diamond. This connects the short copy to the observed black background without speculating about RBG rendering or stale folded literals.

## Regression

`tools/patch_tests/dma_test.cpp` programs the actual on-chip DMA registers with CHCR `0x5E01`. It checks full data, final SAR/DAR, cleared TCR, transfer-end and sixteen untouched tail bytes for lengths 16, 64, 65,536 and 155,040 bytes.

- Before patch: fails length64 at first mismatch16, SAR `00200010`, DAR `06080010`
- After patch: all four cases pass
- Post-patch Python suites: 249 tests and eight subtests pass

Only well-aligned, nonzero TCR cases used by this PAL path are claimed here. Other DMA addressing modes, partial-burst counts and exact timing are not newly validated by these tests.

The original four-patch checkout is preserved separately as `third_party/saturn-recomp-pal-fourpatch-baseline`. The active checkout was reconstructed transactionally from the clean pin plus all five patches; its provenance marker validates successfully. Existing users with a four-patch checkout must preserve it and prepare a fresh five-patch checkout rather than editing the provenance marker or overriding unexpected local changes.

Real-image post-fix screenshot and native-window acceptance results are recorded separately after their runs complete. A successful regression alone does not prove complete gameplay.
