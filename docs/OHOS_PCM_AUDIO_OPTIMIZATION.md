# 鸿蒙 PCM 提交与输出延迟优化（2026-10-14）

后续的 CPU 画面合成和调度优化见 [画面生产与音频供给优化](OHOS_RENDER_AUDIO_OPTIMIZATION.md)。下面是 PCM1 交付路径的独立说明与当时真机结果。

第一轮优化已编译、签名并安装到 MLR-AL10 平板：实际输出回调从 4096 帧 / 92.88 ms 降到 882 帧 / 20 ms，实际 PCM 发布从约 9700 次/s 降到约 176 次/s。片头仍出现源数据不足，尚未达到“连续播放无卡顿”的验收条件。本轮没有修改客体采样、走路速度、游戏逻辑时钟或 host_pace 的追赶策略。

基线为 master `a31141589d6834a0ee957ef7d04e10ab889da997`。优化在 `codex/ohos-audio-pcm` 分支；新增正式补丁 `0023-ohos-pcm-pull-output.patch` 和项目内音频适配器。以下保留 PCM1 实施时的分析记录；最终源码与后续生产、显示及 Windows 修复一起归入本轮发布分支。

## 原因与证据

1. 原 host 请求 SDL 1024 帧，但当前 OHAudio 后端的帧长设置代码被 `#if 0` 禁用，没有调用 `OH_AudioStreamBuilder_SetFrameSizeInCallback`。设备实际返回 4096 帧。后端还存在三块混音缓冲；容量不能直接当作实测端到端延迟。
2. a311415 的初始静音从 100 ms 增到 112.88 ms，只增加 12.88 ms。该预灌能覆盖拉取相位，不能补偿运行中音频生产持续落后。用户报告的外放轻微延迟不能全部归因于这 12.88 ms。
3. 客体每次设备轮询生成约 4–5 帧音频，立即调用宿主。在基线有效 130.123 s 中提交 1,263,617 次，约 9711 次/s；每次查询和提交 SDL 队列都会加锁。合批能去除大量交付开销，但基线没有 CPU 耗时测量，不能将它单独认定为卡顿根因。
4. `sound_tick()` 按 `sat_now()` 生成 44100 Hz PCM，而物理设备持续按真实时间消费。`host_pace()` 落后超过 100 ms 时平移时间基准，放弃追赶。渲染、设备轮询和音频生成处在同一客体执行线程，持续落后会产生实际供给缺额。

新路径实测片头的 80.071 s 中，16 次计时重置放弃追赶共 **1661.808 ms**，音频回调累计缺额 **1650.340 ms**，两者接近。真实 PCM 平均生产 **43170.01 帧/s**，低于物理输出所需 44100。这个结果明确要求继续解决生产与播放的时钟失配；单纯增大起始缓冲无法长期补齐。究竟是渲染、客体计算、读盘还是线程调度造成落后，仍需分段性能测量。

## 已实现的交付与输出路径

```mermaid
flowchart LR
  A[原始客体 PCM<br/>S16 双声道 44100 Hz] --> B[256 帧交付批次]
  B --> C[预分配 SPSC 队列]
  C --> D[鸿蒙播放回调<br/>实际 882 帧]
  D --> E[平板扬声器]
```

- 保留原始 PCM 样本、顺序、数量及声道，只对宿主交付合批。256 帧约 5.8 ms；在画面交付、菜单暂停和结束报告处提交尾部不足一批的数据。
- 使用本项目的 `pal_ohos_audio.cpp` 适配器直接建立 OHAudio renderer，请求 882 帧 / 20 ms、GAME 使用类型和 FAST 模式；查询实际采样格式、回调大小与运行模式。该请求符合普通通路的 20 ms 下限。
- 用一个预分配单生产者/单消费者队列交付数据。播放回调只复制 PCM、填充不足部分及更新原子计数，不分配内存、不加锁、不读客体状态、不查询时钟或写日志。
- 等待真实 PCM 达到三块回调余量再启动；本机为 2816 帧 / 63.85 ms，没有额外起始静音。队列容量维持原有 11025 帧 / 250 ms 上限，容量不等于目标延迟。满队列时对生产者执行有界等待，保留已暂存数据，不淘汰旧样本。
- 宿主菜单、前后台、音频焦点中断通过原子标志控制播放，暂停时保留队列。控制线程执行平台 Start/Pause 和音量控制；平台已暂停时不重复执行非法 Pause。退出时先停止控制线程，再释放 renderer。
- 日志每 5 s 输出生产、提交、实际回调缺额及计时重置丢失时长。控制线程使用 HiLog，避免调用会读取客体时钟的 `sat_note()`。
- 建流 API/获得的格式或小回调不满足要求时使用 SDL 后备路径；`PAL_AUDIO_SDL_FALLBACK` 也可用于受控对比。API 20 的 FAST 状态查询与 API 23 的路线延迟查询动态加载，保持原 API 16 最低兼容要求。

路线匹配 PAL UID 20020280、PID 24791、stream 100088，设备为 SPEAKER，使用类型为 GAME。系统输出管线为 primary 48000 Hz / s32le；44100 是应用客户端格式。系统报告的 45 ms 不包含实时队列占用，不能与启动余量直接相加作为精确声画延迟。

这里的缺额是 OHAudio 回调未能取得的源帧，并非实测硬件 underrun，也不是一次持续 1.65 s 的停顿。当前采集覆盖冷启动和片头，未完成标题页、载入同一存档、走路、战斗、五次菜单循环及后台恢复的整体验收。与旧版标题页统计不是同场景对比，不能直接比较卡顿改善比例。

设备随后进入桌面，PAL 在后台，未继续注入操作或反复拉回前台。测试结束恢复原全局 Debug 日志级别。用户回复当前暂时无法试听，要求继续分析生产端；这不作为无声故障或听感已通过的证据。

后续真机性能采样及不运行采样器的对照已记录在 [生产端分析](OHOS_AUDIO_PRODUCTION_ANALYSIS.md)。当前对话画面的 40.049 s 对照中，生产速率为 39301.26 帧/s，回调源缺额 4340.39 ms，计时重置放弃追赶 4320.86 ms；提交失败、平台错误、生命周期切换和新增满队列等待均为 0。视频路径是首要计算热点，尤其是 VDP2 软件合成；高频主从客体 CPU 切换也有明显开销。该场景与先前片头不同，不能用这两组缺额比例认定版本性能回退。

## 后续综合收敛方案

先定位并减少阻塞客体线程的工作：分别测量 VDP2 合成、纹理上传/呈现、客体声音计算、读盘和调度等待，在同一场景比较生产速率、重置丢失时长和源缺额。可减少重复画面的纹理上传或搬离可分离的宿主 I/O；输入采样、逻辑步进和有效动作帧必须保持原有节奏。最终目标是正常播放期间 PCM 生产跟上设备消费，并且缺额不随时间累计。

输出侧再探测设备是否支持 48000 Hz 的 FAST 通路。若设备证据证明有收益，可保留客体 44100 Hz，单独对硬件输出执行正常的 44100→48000 转换，并按实际 FAST 回调及抖动确定更小余量。当前仅确认 44100 路线为普通通路；不能宣称改成 48000 就一定能启用 FAST。

如果客体与设备时钟仍存在长期小幅偏差，再评估有界、仅音频输出的速率校正或保持音高的时间伸缩。必须单独验证音乐、瞬态音效及声画同步，计数原始源缺额和处理量。它有音质与同步取舍，不作为未测量时的默认补丁。

低延迟队列无法覆盖任意长的生产停顿；解决这种情况需要减少生产端阻塞。重复补静音、大幅扩容或单独让 SCSP/68000 按墙钟跑，都不能替代这一工作。下一轮至少在同一外放路线和存档持续运行 3–6 分钟，覆盖菜单/后台恢复，记录缺额、实际回调和声画延迟，并复核已验收的走路手感。
