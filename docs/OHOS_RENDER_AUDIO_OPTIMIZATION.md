# 鸿蒙画面生产与音频供给优化（2026-10-14）

GPU 已经用于最终画面显示、纹理缩放及 SDL 触控/设置界面，已有真机日志为 `drawing with opengles2`。Saturn VDP1 光栅化和 VDP2 图层合成仍在 CPU 上完成，并与声音生产共用客体推进链。之前测得的视频路径约占主执行线程计算采样的 65%；这不能解释为 ArkUI 控件本身占用 65%，也不能解释为整个渲染过程没有使用 GPU。

当前基线为 master `a31141589d6834a0ee957ef7d04e10ab889da997`，修改位于 `codex/ohos-audio-pcm` 的工作区。保留已经接受的走路规则、客体时钟、原始 PCM 样本及音频输出余量。所有统计中的源缺额均为播放回调取不到源 PCM 的帧数，不能直接视为硬件 underrun 或一次同样长的停顿。

## 实施方案

1. **减少 CPU 合成重复工作（0024）。** 每次 VDP2 合成重新解码调色板、精灵控制、优先级、混色比例及色偏；重复的调色板精灵代码按本次合成的 epoch 缓存。直接 RGB 保留直接解码，图块的二次幂寻址改成等价位运算。每次普通合成或 paired snapshot 都重新建立缓存，避免寄存器、调色板、快照或读档后的陈旧结果。新增静态存储约 1.3 MiB，不在像素循环分配内存。
2. **先检查定向唤醒（0025），再移除高频 OS 线程交接（0026）。** 定向 condition variable 保留为普通平台路径。鸿蒙改用已有 minicoro 的独立 4 MiB 栈，让主从客体 CPU 在同一宿主线程串行交接，保持原来的 safe point、64 次 slave poll slice、SINIT、idle、复位和中断处理顺序。不存在两个客体 CPU 并行修改共享状态，也没有增大客体执行 slice。
3. **保留 SDL 线程与逻辑输入所有权。** 迁移后从客体 CPU 也位于 SDL 主线程，因此生成的输入检查同时要求 `SDL_IsMainThread()` 和 `g_cpu == &g_master`。从 CPU 的宿主调用经主任务和真实线程栈转发；嵌套协程不直接操作另一个协程的栈。宿主回调异常及从 CPU 异常通过 `exception_ptr` 传递，在目标栈重抛。
4. **继续使用 PCM pull 路径（0023），限制恢复积压。** 44100 Hz/S16/双声道原始 PCM，256 帧合批，882 帧实际输出回调；启动余量及 11025 帧存储容量维持 PCM 第一版。PCM4 将发布上限限制为 prime 加一个实际回调，在当前设备为 3840 帧；生命周期恢复延迟通过生产端等待消化，不积累到存储容量。实时回调不运行客体逻辑、不加锁、不分配、不写日志。
5. **后台同时暂停客体生产（0027）。** 后台标志由 SDL 生命周期 watch 以原子方式设置。生产者在真实 SDL 线程栈等待前台，继续处理生命周期及退出事件；恢复时从墙钟 pacing 排除等待。暂停期间保持 PCM 和客体状态，避免播放暂停后继续生产直至队列满。

完整 GPU VDP1/VDP2 合成尚未实施。它需要正确还原精灵/背景优先级、窗口、阴影、透明和混色；当前先用已有 GPU 呈现路径，去掉 CPU 冗余和宿主调度开销。这样可以直接改善 PCM 的生产余量，并用现有软件结果检查画面一致性。

## 对照结果与检查

在 MLR-AL10 上，PCM1 重新恢复至开场李逍遥“哎呀～疼啊！”对话，测得 8 个完整窗口 / 40.045 s，生产 39158.25 帧/s，源缺额 11.186%，放弃追赶 4431.355 ms。前后截图一致，没有平台错误、生命周期切换或新增队列回压。

仅启用合成缓存与定向唤醒的 PCM2，片头至标题页连续 85.058 s 的有效窗口中，生产 44098.84 帧/s，源缺额与计时重置均为 0。但重新进入同一开场对话后，175.155 s 的有效窗口仍只有 39391.64 帧/s，源缺额 10.679%，放弃追赶 18736.576 ms。因此 PCM2 不能作为已解决卡顿的版本，继续实施了 0026 的同线程协程交接。

两个版本均使用同一平板、同一开场台词、相同输出配置，统计期间全局日志暂为 Info，最后恢复 Debug。对话截图在各自版本前后完全一致；旧版本窗口高度为 1534，新版本为 1600，不能将两版截图宣称为跨版本逐像素一致。设备未提供可读的温度和频率文件，也没有严格匹配热状态，以上数字是场景对照，不能当作精确的单项加速比例。

- 合成测试对 576 帧的每个 RGB 像素核对原始固定版本与 0024，涵盖调色板更新、精灵类型、阴影、窗口、混色、高分辨率、交错及连续合成，结果一致。
- 协程测试调用实际 `slave_main/give/to_master/slave_on/slave_off/slave_kick` 及实际任务协程代码，对 6400 次命令、9650 次 slice、6480 次 idle、80 次复位和宿主回调检查完整执行记录，与原线程路径一致；同时覆盖宿主回调抛出、跨栈异常和逻辑 CPU 输入所有权。
- 最新输入/构建相关检查为 189 项通过、125 项 subtest 通过；1 项依赖外部 SDL 测试 SDK 的检查跳过。上一批音频队列、合成、定向唤醒、包身份、手机和 portable 检查通过的部分仍有效；新增 host 身份 fixture 已更新并复测通过。
- Windows 增强运行时完整重新生成和编译成功；鸿蒙 ARM64/x86_64 release 构建成功，原始样本生成、走路常量、VBlank 推进及 pacing 策略未修改。

PCM3 已编译、官方验签并覆盖安装。安装后签名指纹和首次安装时间 `1791698033178` 与原包一致。用户解锁后，实际运行日志已确认 `cached-frame-v1`、`serial-fiber-v1` 及 OpenGL ES 呈现。开场同房间李大娘对话连续 180.175 s / 36 个完整窗口，PCM 生产 44099.29 帧/s，源缺帧、放弃追赶、提交失败、平台及控制错误均为 0，前后截图完全一致。这里已推进至李大娘下一句台词，不能称为与 PCM1/2 完全同台词的逐像素 A/B。

进一步五次菜单开关暴露了暂停恢复积压：队列从约 5000 帧增加至接近 11025 帧容量，约 250 ms，新增队列等待 1342 次，并有一次 103.573 ms 的 pacing rebase。随后后台恢复窗口出现 116471 帧提交失败：鸿蒙不像 Android 那样在后台阻塞 SDL 事件泵，客体还在推进，但播放已经暂停。因此 PCM3 解决了前台持续生产欠供，却不能作为完整验收版。

PCM4 为此增加两个控制：发布上限为真实 PCM prime 加一个实际回调，并按 256 帧合批向上取整；当前 2816+882 得到 3840 帧 / 87.07 ms，环形存储容量仍为 11025 帧。超过发布上限时生产端等待消费，不移除旧 PCM，也不修改样本。0027 在进入后台时将生产挂到真实 SDL 线程栈，继续轮询生命周期/退出事件；恢复后从墙钟 pacing 扣除整段等待时间，保持前台客体执行和走路规则。新队列测试核对预算改变后的样本保留和真实并发；后台测试执行实际补丁中的等待代码，覆盖恢复、退出及异常。
