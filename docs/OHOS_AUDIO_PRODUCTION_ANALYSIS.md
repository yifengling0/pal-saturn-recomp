# 鸿蒙 PCM 生产端分析（2026-10-14）

后续实施与逐版真机对照见 [画面生产与音频供给优化](OHOS_RENDER_AUDIO_OPTIMIZATION.md)：已增加 VDP2 帧内解码缓存、定向唤醒和鸿蒙串行 CPU 协程；以下保留 PCM1 的原始分析证据。

当前最明确的性能热点是视频软件合成与主从客体 CPU 的线程切换。音频合成也有成本，但已优化的 PCM 交付开销很小。生产端在墙钟时间内推进不了足够的客体时间，`host_pace()` 又会在落后超过 100 ms 后放弃追赶，导致源 PCM 长期不足。扩大输出缓冲只能延后队列耗尽。

继续使用已安装的 `a311415-pcm1` 测试包，本轮增加性能采样与分析证据。用户当前暂时无法试听；外放延迟、断续和爆音仍待听感验证。走路时序、音频合成语义、逻辑时钟、主从切换顺序与追赶策略均保持原实现。

## 无采样器对照

PID 24791 保持前台。初始恢复后的画面为游戏地图，随后进入开场剧情。正式对照前后是同一幅李大娘对话画面，两张 PNG 的 SHA256 相同。本轮没有注入游戏按键。对照期间仅做间隔 10 s 的前台与既有日志检查，不运行 hiperf。全局日志暂设 Info，结束恢复原 Debug。

统计为 8 个完整的既有 5 s 日志窗口，设备原始时间 08:35:02.152 至 08:35:37.195。每条日志覆盖此前约 5 s；合计时长不是首末日志时间戳之差。

| 指标 | 当前对话画面 |
| --- | ---: |
| 有效窗口总时长 | 40.049 s |
| 接受的源 PCM | 1,573,976 帧 |
| 平均生产速率 | 39,301.26 帧/s |
| 请求的源帧 | 1,766,646 帧 |
| 缺额 | 191,411 帧 / 4,340.39 ms / 10.835% |
| 放弃追赶次数 / 客体时间 | 42 / 4,320.857 ms |
| 提交失败 / 平台错误 / 控制错误 | 0 / 0 / 0 |
| 生命周期切换 / 新增满队列等待 | 0 / 0 |
| 回调帧长 / 实际最大帧长 | 882 / 882 |

源缺额与放弃追赶仍只相差约 19.5 ms。物理回调约每 20 ms 请求 882 帧，而源生产只达到所需速率的约 89.1%。队列占用在本段为 256–2156 帧，远低于 11025 帧容量。`backpressure` 是累计计数，本段前后均为 1579；不能把该数当作本段发生了 1579 次等待。

这是回调源缺额，不是一次持续 4.34 s 的停顿，也不是硬件 underrun 测量。先前片头 80.071 s 的生产速率是 43170.01 帧/s，缺额 2.061%；场景和设备运行条件不同，不能据此认定版本回退。当前证据也没有测得温度和核心频率，不能把差异归因于温控。

## 性能采样定位

使用当前 release 包直接采样，保留本地性能文件，不需要替换安装包：

- 20 s，`sw-cpu-clock`，199 Hz，FP 调用栈，4114 个样本，无丢失。
- 15 s，`hw-cpu-cycles`，99 Hz，FP 调用栈，6478 个样本，无丢失。
- 另有 20 s 包含 off-CPU 的辅助采样，用于观察等待路径；其所有线程时间相加超过墙钟窗口，不能当作 CPU 使用率。

两种纯计算采样的主执行线程结果一致：

| 路径 | 软件 CPU 时钟采样权重 | 硬件周期采样权重 |
| --- | ---: | ---: |
| video_tick 及其后续调用 | 64.47% | 约 65% |
| VDP2 合成调用位置 | 42.07% | 42.61% |
| sound_tick 及其后续调用 | 13.71% | 13.34% |
| PCM push / publish 可识别路径 | 低于 0.1% | 低于 0.2% |

这些是主线程的采样权重，不是整机 CPU 占用，不同包含路径不能相加。它们也不衡量渲染阻塞期间的墙钟等待。采样场景包含开场剧情过渡，正式无采样器对照是之后的固定对话画面，不能当作严格的前后性能对比。

当前 HongMeng 采样记录存在无效的顶层 IP，部分最内层函数没有出现在可恢复的 FP 栈中。仅凭自动报告，会把大块工作记成 `video_tick()` 自身或 `sound_tick()` 自身。进一步检查最近可恢复帧的返回地址，并核对当前包对应 ELF 的反汇编：

- `0x17f88c` 紧接 `vdp2_compose()` 调用，软件时钟采样中主线程 2691 个样本有 1132 个集中于此；硬件周期采样中 1676 个样本有 685 个集中于此，按周期权重占 42.61%。这定位了软件合成调用路径，不能进一步划分它内部每条像素运算的成本。
- `0x18bbc0` 紧接 `scsp_sample()` 调用，软件时钟采样中有 232 个样本。
- `0x18bd18` 紧接 `m68k_execute()` 调用，有 90 个样本；只读函数名统计会漏记这部分声音 CPU 工作。

本地未剥离和 HAP 构建所用剥离 ELF 的 Build ID 均为 `91776fa4d776111560cfee81fa298a7603a1db01`。源码与最终包身份沿用 PCM 优化报告中的已验证结果。

VDP2 在每个 VBlank 为整幅画面执行软件合成：遍历每个像素、解析精灵类型及优先级/调色板、读取背景图块、判断窗口、选择两层并计算混色和色偏。主线程的 VDP1 线段光栅化也是明显热点，最近可恢复的 `line()` 路径约占 12%，而不是单纯纹理上传造成全部成本。`SDL_RenderPresent` 还经过 EGL、NativeWindow 和 Surface IPC，存在可见的宿主调用路径；当前证据不足以给它分配精确的阻塞毫秒数。VSync 已经关闭。

## 主从切换与生产时序

声音、设备轮询和画面交付都由主客体执行线程推进。设备轮询顺序是先 `video_tick()`，再 CD/SMPC，最后 `sound_tick()`；视频合成、呈现或 pacing 的停顿会直接延后下一批 PCM。

从 SH-2 采用另一个宿主线程充当协程，主从通过 mutex、condition variable 和 `notify_all()` 来回交接；客体没有并行执行。10 s 辅助计数记录主线程 69,582 次、从线程 67,121 次上下文切换，约每秒数千次。硬件周期采样中，从线程约 69.2% 的权重在通知路径、20.4% 在条件等待路径，实际客体计算占比较小。切换计数也包含系统调度，不能全算成程序主动交接；hiperf stat 的部分时间/速率注释明显异常，本报告只保留原始计数和独立采样权重，不采用其 CPU 使用率注释。

这意味着主线程既承担逐像素渲染，还会频繁阻塞并等待从线程返回。生产落后可以由计算成本和唤醒/调度等待共同造成，不能根据平均 CPU 占用就排除调度。

音频按 `floor(sat_now() * 441 / 10000000)` 生成，恰好是客体时间的 44100 Hz；4–5 帧的短批是约 102.4 µs 轮询粒度的自然结果。该公式没有每次轮询累积向下取整的采样率误差。视频行周期的整数截断为每帧 208 ns，约 12.47 ppm，80 s 约 1 ms，远小于已记录的秒级缺额。

## 下一轮优化顺序

1. **先减少 VDP2 软件合成的重复工作。** 在一次 compose 内缓存精灵控制、优先级、混色比例、色偏及调色板解码；把可按帧/扫描线预计算的数据移出像素循环。帧内客体状态不会并发变化，缓存仍须绑定当前普通视图或 paired snapshot。用相同输入逐像素比较 RGB、阴影、透明、窗口和混色结果，再在设备相同场景对照。不能简单认为每个寄存器读取都独立贡献了 42%；内部优化收益仍需验证。
2. **再减少主从交接的宿主调度成本。** 评估同一线程的栈式协程，保留现有 safe point、slice、SINIT、空闲、重置和中断交接顺序。现有运行时已有 minicoro，但替换这条切换路径需要验证任务协程嵌套和异常；不能直接让两个 SH-2 并发读写全局状态，或调大 slice 改变客体执行顺序。
3. **按证据优化 SCSP/68000。** 缓存可在寄存器写入时更新的解码数据，保留每个源采样、定时器、DSP、IRQ 与声 RAM 交互。声音独立按墙钟运行会改变与主客体的交互，不作为默认方案。当前 PCM 交付合批已有收益，继续加大批次不是首要方向。
4. **生产稳定后再缩小输出余量。** 当前小回调无法掩盖 10% 级供给缺口。先在同一存档、同一外放路线持续观察源缺额和重置丢失时间，再评估更小启动余量及 48000 Hz FAST 通路。普通采样率转换本身不能补齐客体时间不足。

本轮可以确定优先级和供给失配机制；还不能声称某一项优化已经消除了卡顿。下一版应保留原始源缺额计数，以生产稳定、RGB/PCM 语义一致及已验收走路手感作为检查依据。
