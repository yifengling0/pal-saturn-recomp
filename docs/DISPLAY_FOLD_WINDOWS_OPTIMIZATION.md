## 显示和调整

- **适应 / Fit**：使用实际游戏纹理宽高比，等比放大到可用画面区域的最大尺寸。一边铺满，另一边居中留边。与横向、纵向设备都兼容。
- **拉伸 / Stretch**：横纵两轴铺满可用画面区域，允许比例变化。
- **4:3**：原“电视”选项，保留原始 PAL 电视画布和留边行为；菜单附“原始电视比例和留边”说明。
- **鸿蒙屏幕方向**：横屏、竖屏、自动，默认横屏；自动允许随设备旋转。方向请求通过 NAPI 线程安全事件交给现有主窗口，不轮询、不重建 SDL 表面。
- **鸿蒙画面分区**：普通横屏只显示自动、叠加、左右；普通竖屏只显示自动、叠加、上下。左右把游戏放左边、按键放右边；上下把游戏放上方、按键放下方。手动分区随实际表面宽高变化，旧的 `below` / `right` 配置也遵守这条规则。画面占比可在 30%–70% 调整，默认 60%。恢复画面回到横屏、适应、自动、60%。
- **按键调整**：沿用移动按键入口、分组拖动和完成/取消流程；大小、间距、透明度继续可调。分区位置使用独立 `split_` 设置，切回叠加恢复普通位置。狭长右侧控制区域把十字键放上方、六键放下方；宽区域保持左右手布局。新触点被限制在控制区，已经捕获的方向拇指仍保留原来的滑动和走路规则。
- **Windows**：即使导入 `layout=right` 等移动设置，也强制整窗口叠加；菜单没有鸿蒙的分区、占比和恢复分区行。普通画面模式和既有触屏编辑功能保留。F10 打开宿主设置，Esc 保留游戏菜单/取消；最终分发 README 已核对这一区别。

参考了 [PPSSPP 显示布局](https://github.com/hrydgard/ppsspp/blob/master/UI/DisplayLayoutScreen.cpp)的比例、拉伸、实时调整及恢复默认，以及 [PPSSPP 按键布局](https://github.com/hrydgard/ppsspp/blob/master/UI/TouchControlLayoutScreen.cpp)的分组拖动、大小和间距调整。也核对了 [RetroArch 配置](https://github.com/libretro/RetroArch/blob/master/retroarch.cfg)及[触控覆盖层说明](https://github.com/libretro/docs/blob/master/docs/guides/libretro-overlays.md)。实现为本项目自有代码，没有复制这些项目的实现。

## 折叠形态

ArkTS 在现有主窗口生命周期中独立订阅折叠、显示模式、显示变化和窗口尺寸事件，80 ms 合并更新。XComponent 保持存活，只把实际表面位置、尺寸及折痕信息传给小型 NAPI 桥接库；SDL 游戏线程读取一致的几何快照。区域改变时清除旧触点、方向账本及拖动状态。

自动布局仅在半折且存在有效中央折痕时分区，并避开实际折痕宽度；这一特殊形态按真实折痕方向分区。展开、合拢或几何不可用时恢复叠加。横屏/竖屏/自动设置决定允许的旋转方向，半折不会覆盖用户明确选择的方向；桌面或书本姿态可选自动旋转。普通设备也监听窗口尺寸变化，旋转时清除旧折痕几何，待表面尺寸更新后重新计算。

API 20 及以上使用当前显示方向的 `Display.getLiveCreaseRegion()`，并核对窗口 displayId、折痕所属显示及表面偏移。API 16–19 的旧接口不保证旋转坐标，因此只在 rotation=0 时使用；其他方向保守回到叠加，可手动选择分区。没有折叠真机，本轮不能宣称真实折叠形态、折痕定位或全部设备姿态已经验收。

## Windows 性能与 PCM

Windows 启用与鸿蒙相同的主从客体 CPU 串行协程，以及 VDP2 帧内解码缓存，保持原来的 safe point、slice、复位、中断和宿主调用顺序。最终呈现仍通过 GPU；实际 Windows 运行日志为 `direct3d11`，鸿蒙沿用 OpenGL ES。VDP1/VDP2 客体光栅合成仍由 CPU 完成。

Windows 输出仍为 SDL/WASAPI，44100 Hz、S16、双声道原始 PCM 每 256 帧原样合批。样本帧请求为 512，实际设备报告 441 帧 / 10 ms。初始余量为一个实际设备周期加 40 ms，范围 50–100 ms；当前为 2205 帧 / 50 ms。正常发布上限按余量加一周期及合批向上取整，当前为 2816 帧 / 63.85 ms；这是源队列预算，不是实测端到端扬声器延迟。

超过正常预算时生产端等待消费，避免菜单恢复后积累到 250 ms。每次等待最多 100 ms，然后回到既有硬上限策略，不能保证系统故障或长时间调度停顿下绝对不丢弃。菜单暂停保留未满一批的 PCM，普通暂停不增加恢复静音。回调只记录计数，不执行客体逻辑或日志。

早期与鸿蒙编译并行的测试曾出现约 83 ms 供给间隔和源短缺；较小 30 ms 余量也曾遇到 43 ms 间隔。因此最终采用 50 ms 最小余量。本轮最终 Direct3D11/WASAPI 连续运行 7200 VBlank / 120.116 s，实际合批均为 256 帧；接受 5296896 帧，源短缺、源队列空观察、丢弃、提交/查询失败均为 0，最大供给间隔 50.362 ms，设备回调全部在独立线程。包含片头至游戏推进过程，不等同于所有场景或主观听感零卡顿。
