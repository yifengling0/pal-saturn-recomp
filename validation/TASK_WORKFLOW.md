# Linux-first 执行与验收流程

## 约束与原则

1. 以 Linux 实测为当前目标。旧实施方案里的 Windows 优先次序被本轮要求替代。
2. 工具链证据、合成夹具证据与《仙剑》实盘证据分别记录；任一层通过不自动提升下一层。
3. 原盘及用户存档只读保存；提取、生成代码、日志、临时存档各自放独立构建目录。运行游戏时使用 `--save -` 或独立测试存档。
4. 不编造游戏文件名、SH-2 地址、配置、成功截图、走路故障根因；未知值显式为 null / unknown / blocked。
5. 本地准备工程不授权发布仓库、上传商业资源、下载商业 ROM 或 BIOS，也不使用其他项目正在占用的桌面/图形会话。

## G0：Linux 工具链与自主夹具

输入：固定的公开上游源码、编译工具、自写合成程序。输出：准确版本、命令、日志、退出码；原生 C++ 指令测试结果和 headless 夹具结果如实际运行。

- 上游固定提交见 README；参照 `tools/check.sh`，区分 Python 测试、指令语义测试、运行时单测与可选 GPL 渲染分支。
- 自写 SH-2 算术夹具要与独立数学期望比较；未知入口负向测试不能跳过。
- 合成光盘只证明解析、编译、运行时最小通路；不是《仙剑》，也不保证可在真实 Saturn 开机。
- `--interp` 是画面插值选项，不是 SH-2 解释器模式；不得用它来判断是否真正静态重编译。
- 上游执行授权或构建依赖阻塞时明确记录，不把“脚本已写好”计为执行通过。

验收：相关检查确实跑完且日志可复核。即便全部通过，G1～G5 仍未验证。

## G1：真实游戏镜像身份、布局与代码入口

输入：用户合法持有的 CUE + 全部轨道，或待单独转换验证的 CHD；版本/语言/补丁情况。

1. 运行 `pal_validate prepare`，保存输入 SHA-256、来源说明、轨道与 ISO 目录。
2. 对实盘 IP.BIN 中 product/title/version/areas 做版本核对。参考资料中台湾版 `T-37401H` 和日版 `T-37401G` 只作核对线索，不能替代实盘读取；也不要把 PAL 简称当成欧洲区。
3. 获取首读文件的真实路径和装载声明；检查实际加载代码、crt0、跳转轨迹、内存边界及可执行范围。
4. 对每个模块记录文件哈希、装载/入口证据、overlay 生命周期、函数种子及不确定项。使用 `examples/module_evidence.template.json`，没有证据的字段不填。
5. 捕获可执行区写入、缓存相关寄存器/数组操作、模块切换；确定生成代码是何时、按何种原始字节映射到运行时内存。
6. 只有有据可查的模块和入口才能写成游戏 `game.toml`，再调用上游生成/构建。上游例子中的地址一律不得直接照搬。

验收：真实版本身份、完整轨道、SH-2 模块及入口各有可复核证据。`--find-base` 分数只能是候选；IP.BIN 的装载地址不能当作已执行入口。

## G2：启动至标题并覆盖关键对白

输入：通过 G1 的配置、原盘及固定编译参数。

- 保存真实编译命令、生成代码清单、构建日志。
- 从干净专用存档启动，记录 boot→标题、异常入口/返回、模块切换、音画证据。
- 有未知入口时，先确认地址属于真实代码，再学习种子、重编译、重跑。不能靠随意跳过异常来凑成功。
- 明确验证台湾/日版各自的缓存敏感连续对白。Mednafen 公开文档要求该游戏完整 SH-2 cache 模拟来避免文字截断；本固定上游尚无等价完整缓存模型。
- 不将 cache / SMC 风险直接归因成走路问题。只有明确写入和执行轨迹后才能决定对策。

验收：可复现启动、标题和对白关键路径；没有被忽略的未知代码调用，画面和文字对照明确。

## G3：可操作地图、输入和回归

输入：固定版本游戏、通过 G2 的构建、可复现按键脚本。

- 验证首张可操作地图；方向输入、交互、菜单、地图切换、碰撞、连续对白、存读档分别留证。
- 记录基于 VBlank 的原始输入脚本，但与参考实现比较时按已验证的游戏逻辑 tick/场景状态对齐；不同 BIOS/光盘读取速度不能硬用相同 VBlank 当相同游戏时刻。
- 每次重复固定随机种子/RTC/存档及相同路径；不能复用玩家日常存档作为自动测试输出。

验收：按键可回放并达到相同场景/状态，主要路径至少重复两次。达到此 Gate 才开始评价走路现象。

## G4：走路基线、诊断和改动验证

按 [WALKING_BASELINE.md](docs/WALKING_BASELINE.md) 执行：逻辑 tick、世界位移、动画帧、镜头位移、碰撞与渲染呈现分别记录。先证明现象并定位影响它的真实代码/变量，再讨论修复。

- 任何修复必须有参考基线、相同输入下的前后差异和非走路回归。
- 不能以宿主 FPS 上升作为步速/动画正确的证明；也不能通过简单乘倍移动常数来代替根因调查。
- 画面插值可独立实验，但不得改变逻辑速度、碰撞和脚本时序。

验收：各坐标及计数器语义已证实；诊断证据充分；改动可重复、可回滚、没有引入其他路径退化。

## G5：原生 HarmonyOS 后续工程

前置：Linux 游戏基线稳定且 G4 结论明确。

- 使用当前官方 SDL3/OHOS 工具链核验生成器是否能产出正确共享库，接入 HAP 工程、Native 生命周期、输入、音频、文件授权、沙箱与持久化。
- 现有 Android shared-library 分支不等于 OHOS 已支持；需要独立构建和真机验证。
- OHOS 上复用同样的逻辑 tick / 输入 / 状态回归，另测触控、切后台、音频恢复、存档及性能。
- 正式签名和发布独立请求授权；此轮没有任何 OHOS 可运行结论。

## 失败处理与结束条件

缺盘：保留报告和下一步命令，G1 显示 `blocked-input`；不继续编造游戏配置。上游检查失败：先保存退出码和日志，在已授权范围内定位并重新验证。权限缺失：暂停对应执行，说明所缺授权；已完成的只读/自有测试不撤销，也不标为完整通过。用户提供新镜像或授权后从相应 Gate 继续。
